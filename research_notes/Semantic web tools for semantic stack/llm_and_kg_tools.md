## Key question 1: MCP servers for the semantic web (SPARQL, Wikidata, rdflib, OWL/ontology, GraphDB/Stardog/Neo4j, LinkML, SHACL, Comunica) and which are generic enough for QLever/Fuseki/Oxigraph

### Takeaway
There is no dominant "SPARQL MCP" yet; the field is a long tail of small (0-130 star) servers, most created 2025-2026. The best generic candidates that can point at QLever/Fuseki/Oxigraph today are rareba/sparql-mcp (stdio, read-only, any SPARQL 1.1 endpoint, pip), Kashif-Rabbani/mcp-server-sparql (SSE, read+write+Graph Store Protocol+SHACL validation), sib-swiss/sparql-llm's MCP (HTTP/stdio, RAG-assisted NL-to-SPARQL, needs VoID/SHACL metadata), comunica-feature-mcp (official Comunica, local files/HDT/Solid/link traversal) and XORwell/mcp-server-qlever (QLever-specific, GHCR image). For ontologies, fabio-rovai/open-ontologies (1,054 stars, Rust on Oxigraph, GHCR image, MCP stdio+HTTP) is the clear leader. The only vendor-official servers are Wikimedia Deutschland's WikidataMCP, Comunica's, Stardog Cloud's (SaaS-only) and Graphwise/GraphDB's (built into GraphDB 11, proprietary); Zazuko, Ontotext (as separate OSS), LinkML and SHACL have no dedicated MCP server that I could find.

Benchmarks of SPARQL-MCP agents

- "Agentic SPARQL: Evaluating SPARQL-MCP-powered Intelligent Agents on the Federated KGQA Benchmark" (Dobriy, Bauer, Azzam, Banerjee, Polleres; submitted 2026-01-20, v2 2026-04-09) connects LLM agents to SPARQL endpoints via MCP for endpoint discovery, schema exploration and federated query formulation — [arXiv 2603.06582](https://arxiv.org/abs/2603.06582).

### Inferences
- For semantic-stack, the lowest-risk additions are (a) XORwell/mcp-server-qlever as a sidecar container (it already has a GHCR image and QLever-specific tools such as autocomplete and query plans) and (b) a generic read-only server pointed at Fuseki/Oxigraph. Among generic ones, rareba/sparql-mcp is the cleanest read-only stdio option but has no Docker image (trivial to wrap); Kashif-Rabbani's is the only one covering SPARQL Update + Graph Store Protocol + SHACL over HTTP/SSE, which maps 1:1 onto Fuseki's `/query`, `/update`, `/data` layout, but it must be network-isolated because it exposes DROP/CLEAR.
- Because Claude Code supports both stdio and HTTP MCP, a compose service exposing Streamable HTTP (cyanheads-style, open-ontologies, Web-Algebra) is more "stack-like" than a stdio binary the user must launch locally; stdio servers can still be documented as `claude mcp add` snippets.
- open-ontologies' star count (1k in seven months) and GHCR image make it the strongest "ontology engineering for agents" candidate, and it already embeds Oxigraph, so it does not need the stack's Oxigraph.
- Almost every server here is a one-person project with 0-55 stars; maintenance risk is high. Vendoring a pinned image/commit is advisable.

## Key question 2: Text-to-SPARQL / natural-language querying tools, benchmarks and self-hostable chat-over-KG UIs (2025-2026)

### Takeaway
The reference open-source NL-to-SPARQL system in 2026 is SIB's sparql-llm (MIT, 127 stars, PyPI 0.1.4), which won the TEXT2SPARQL 2026 challenge at ESWC 2026 and ships a Docker Compose chat UI + MCP server, but it needs VoID/SHACL metadata per endpoint and documents only OpenAI-compatible APIs. LangChain's GraphSparqlQAChain still exists in langchain-community but has moved to the legacy path; LlamaIndex has pivoted to property graphs; Haystack/DSPy show no SPARQL integrations. Self-hostable "chat with your KG" UIs are sparql-llm's chat, flexible-graphrag (Anthropic + Ollama supported, Fuseki/GraphDB/Oxigraph backends) and GraphDB's proprietary Talk-to-Your-Graph.

### Cited Findings

- TEXT2SPARQL 2026 was the second edition, co-located with ESWC 2026 (Dubrovnik, 10 May 2026); eight approaches competed; SIB's SPARQL-LLM ranked first, with up to 59% higher accuracy than the second-best; F1 was reported on DBpedia (EN/ES) and a Corporate KG (EN/DE); second-best was ARUQULA v1 and GRASP also appears in the results table — [arXiv 2610.13648 "SPARQL-LLM in the TEXT2SPARQL 2026 Challenge"](https://arxiv.org/abs/2610.13648), [challenge guidelines](https://text2sparql.aksw.org/2026/guidelines/). The challenge website repo is AKSW/text2sparql.aksw.org (CC-BY-SA-4.0, pushed 2026-07-20) and a CLI client AKSW/text2sparql-client (Apache-2.0, pushed 2026-04-10) exists — [GitHub API](https://github.com/AKSW/text2sparql.aksw.org), [GitHub API](https://github.com/AKSW/text2sparql-client). Participant write-ups in CEUR Vol-4094, e.g. AIRI team — [ceur-ws.org/Vol-4094/paper5.pdf](https://ceur-ws.org/Vol-4094/paper5.pdf).
- sib-swiss/sparql-llm — MIT, 127 stars, created 2024-05-15, pushed 2026-10-13; "Chat system, MCP server, and reusable components to improve LLMs capabilities when generating SPARQL queries" — [GitHub API](https://github.com/sib-swiss/sparql-llm). ### Inferences
- sparql-llm is the only NL-to-SPARQL project with a maintained Docker Compose deployment and a challenge win; integrating it into semantic-stack would require (1) generating VoID for the QLever/Fuseki datasets (void-generator), (2) authoring a handful of SHACL-described example queries, and (3) routing Claude through an OpenAI-compatible gateway (e.g., LiteLLM) since Anthropic is not documented natively.
- Given the warnings in LangChain's own docs and the deprecated-lookup move, GraphSparqlQAChain should be treated as legacy; the rdflib-orm/surfrdf submodules plus an MCP server give Claude Code a more direct path than a LangChain chain.
- The emerging pattern (Cagle, Agentic SPARQL paper, sparql-llm) is "retrieve schema/examples -> generate -> validate against VoID/SHACL -> execute", not raw zero-shot generation; any addition should expose schema-introspection tools (classes, predicates, VoID) rather than just a `query` tool.

## Key question 3: GraphRAG with RDF, ontology-grounded RAG, semantic-layer tools, RDF embeddings and vector+SPARQL hybrids

### Takeaway

## Key question 6: What practitioners are saying (2025-2026) about KGs + LLMs, ontology-driven agents, semantic layers, MCP + SPARQL

### Takeaway
The 2025-2026 practitioner conversation has converged on three themes: (1) "semantic/context layer" as the governance surface agents need (Sequeda: 44% of orgs implemented a semantic layer in 2025, only 1 in 7 governed); (2) MCP as the runtime bridge between graphs and agents, with Cagle arguing for deterministic named queries rather than free-form LLM SPARQL; (3) "vibe ontologies" needing ontologist judgment (Allemang's CDL 2026 talk; Barrasa's ontology-quality series). Direct LinkedIn posts were hard to retrieve via web search; most evidence is from Substacks, newsletters and conference programs.
